# #812 — Transiciones seguras de estado de cita veterinaria

El endpoint veterinario `PATCH /appointments/:id/status` actualizaba cualquier cita del tenant a cualquier estado permitido por Zod, pudiendo «reabrir» silenciosamente una cita `completed`, `cancelled` o `no_show`. Esta entrega añade la autoridad pura `allowedVetAppointmentPreviousStatuses` y la incorpora **dentro del UPDATE SQL** con `a.status=ANY($6::text[])` para evitar una comprobación previa susceptible de carrera. Se mantiene el ámbito por tenant y se exige que el animal asociado pertenezca al mismo tenant. Cuando el UPDATE no afecta filas, una consulta acotada distingue `409` por transición inválida de `404` por cita ausente, sin datos de otro tenant.

El grafo permite un ciclo razonable: scheduled→confirmed/checked_in/cancelled/no_show, confirmed→checked_in/cancelled/no_show, checked_in→in_progress/cancelled, in_progress→completed/cancelled; no permite cambiar ni reabrir estados terminales. Esta regla restringe **solo** el endpoint veterinario de estado. Una ruta genérica de edición de citas del módulo clínico puede requerir reconciliación posterior; no se presenta una autoridad completa hasta proteger todas las rutas de mutación.

Evidencia focal: 6/6 pruebas ejecutadas en V8 sobre los archivos publicados, evaluando transiciones permitidas/prohibidas y verificando el predicado SQL de una sola sentencia, errores 409/404 y el aislamiento tenant. No se ha ejecutado una transacción PostgreSQL17 real, ni navegación clínica, dos escritoras concurrentes, control horario, silla/profesional o un E2E veterinario. #812 continúa OPEN. Sin cambios de esquema/finanzas/workflows ni desactivación de checks.
